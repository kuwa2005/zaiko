# 在庫管理ツール 業務分析と新システム要求仕様

## 1. 概要

- **対象**: `在庫管理ツール.xlsm`（Excel + VBA）＋ `data.accdb`（Access DB）
- **構成**: 11シート・30モジュール・6つのUserForm・5テーブル・6クエリ
- **位置づけ**: 「発注依頼 → 受付 → 入庫 → 出庫」の一連の在庫業務と、商品マスタ（在庫マスタ）・月次入出庫状況の管理を行う単独運用ツール
- **運用前提**: `.xlsm` と `data.accdb` は**同じディレクトリ**に配置（`マニュアル.txt`）。DBは `ThisWorkbook.Path & "\data.accdb"` を `OpenDatabase` で直接参照（`共通.bas` の `DB_OPEN`）
- **解析の前提**: 提供された `data.accdb` は**実データ0行のテンプレート状態**（採番テーブル=0のみ）。列マッピングはVBAコードとクエリ参照から復元したものであり、一部は推定

---

## 2. 業務分析

### 2.1 業務プロセス全体像（フロー）

```
【発注依頼フロー】
  メイン画面「発注依頼」ボタン
    → 担当者チェック → 在庫マスタを読み込んで非表示参照
    → 発注依頼シート(下書き一覧)表示
        ├─「作成」→ 発注登録画面(フォーム)で1件入力 → 下書き一覧に追記
        ├─「依頼」→ 下書き行を一括で T_在庫発注データ に INSERT（依頼確定）→ 下書きクリア
        └─「削除」→ 内容欄="削除" の行を下書きから除外（DBには未反映）
            └─「発注状況検索」→ 発注状況確認画面へ（戻り先フラグ T1=発注依頼）

【受付フロー】
  メイン画面「受付」ボタン → 未受付データ（受付日 IS NULL）を表示
    ├─「印刷」→ 内容欄="出力" の行に 受付者・受付日 をセット → 発注依頼表に転記して印刷
    └─「削除」→ 内容欄="削除" の行を物理削除（DELETE by 管理NO）

【入庫フロー】
  メイン画面「入庫」ボタン → 全発注データ（管理NO降順）を表示
    ├─「保存」→ 内容欄="入庫"=入庫者・入庫日セット / "入庫取消"=入庫者・入庫日をNULL化
    └─「削除」→ 内容欄="削除" の行を物理削除

【出庫フロー】
  メイン画面「出庫」ボタン → 在庫マスタ全件を表示
    → コード列ダブルクリック → 出庫登録画面で出庫数量を入力 → T_出庫データ に INSERT
    → 「出庫確認」→ 出庫実績一覧を表示 → ダブルクリック → 出庫変更画面（変更/削除）

【月次締め・分析フロー】
  メイン画面「入出庫状況確認」ボタン
    → 前月残・当月入庫・当月出庫・当月残を金額付きで集計表示
    → 在庫0/安全在庫割れ/発注予定の警告行を表示
    → 「一括変更」→ 当月残(I列)を T_在庫マスタ.残数量 に一括反映（月次締め）
```

### 2.2 登場する主体・画面・帳票

- **担当者**: メイン画面N5で選択（P5:P11のプルダウン。デフォルト値"担当A"）。依頼者・受付者・入庫者・出庫者・登録者として各伝票に記録される。担当者未選択だと全ボタンが `担当者を選択して下さい。` で停止
- 発注依頼表（帳票）用の承認欄シート（作成/審査/承認）が存在するが、**未使用**（後述）

### 2.3 データモデル（テーブル・カラム・関係・状態）

**T_在庫マスタ**（商品マスタ）: コード※, 品名, 数量（基本数量）, 単位, 単価, 残数量, 安全在庫数, 最小発注数量, 標準納入日数, 棚番, 取引先, 登録者, 登録日, 備考

**T_在庫発注データ**（発注伝票）: コード, 品名, 数量, 納期, 型式, 依頼者, 依頼日, 受付者, 受付日, 入庫者, 入庫日, 管理NO※, 備考
- 管理NO: `"H" & Format(n,"0000000000")`（採番テーブルから採番、排他なし）

**T_出庫データ**（出庫実績）: コード, 品名, 出庫数, 出庫者, 出庫日, 管理NO※, 備考
- 管理NO: `"S" & Format(n,"0000000000")`（採番テーブルから採番、排他なし）

**T_採番テーブル**: 手配管理NO(整数), 出庫管理NO(整数)。Read→+1→Write（排他制御なし）

**T_在庫使用量データ**（休眠）: 対象月, 作番, SEQ, レベル, 親図, カテゴリ, 子図番, 品名, 単位, 数量, バルク, 使用量/ロット, 使用量合計, 登録日
- **VBAから一切参照されない休眠テーブル**。製造計画連動の部品使用量管理の設計意図（C19）

**Accessクエリ**（SQL本文は抽出不可のため推定）
- `Q_発注状況確認データ`: T_在庫発注データ に T_在庫マスタ をJOINし 基本数量/単位/単価 を導出（推定）。発注状況確認・発注状況詳細確認で使用
- `Q_入出庫状況確認`: T_在庫マスタ に当月入庫数/当月出庫数を集計JOIN（推定）。入出庫状況確認で使用
- `Q_入庫データ集計` / `Q_出庫データ集計`: コード別の月間入庫/出庫数量集計（推定）
- `Q_使用量データ集計` / `Q_コード別使用量統計`: T_在庫使用量データの集計（休眠機能）

**状態の表現と遷移（発注→受付→入庫）**

| 状態 | 表現（現行） | 遷移条件 |
|---|---|---|
| 下書き | 発注依頼シート上の行（DB未登録） | 発注登録画面で追記、依頼ボタンで確定 |
| 未受付 | 受付日 IS NULL | 依頼で確定直後 |
| 受付済み・未入庫 | 受付日 NOT NULL かつ 入庫者 IS NULL | 受付画面で「出力」→受付者・受付日セット |
| 入庫済み | 入庫日 NOT NULL | 入庫画面で「入庫」→入庫者・入庫日セット |
| 入庫取消 | 入庫者/入庫日 NULL に戻す | 入庫画面で「入庫取消」（入庫済み行のみ） |
| 削除 | 物理DELETE | 受付/入庫画面で「削除」 |

※入庫取消は入庫済み行（C列="入庫済み"）のみ有効、入庫は未入庫行のみ有効（`⑤入庫マクロ` の `入庫者及び入庫日セット` のC列判定）

### 2.4 業務ルール一覧

| ID | ルール | 実装箇所 |
|---|---|---|
| R1 | 担当者（メインN5）未選択なら全業務を拒否 | `共通.bas` 担当者チェック |

| R3 | 納期は **本日±300日** の範囲（ComboBox）で選択 | `発注登録画面` UserForm_Activate |
| R4 | コードは**半角・大文字に正規化**して入力（重複防止） | `関数.bas` 半角変換/大文字変換 |
| R5 | 在庫マスタのコードは**重複登録不可** | `在庫マスタ登録画面` 登録データチェック |
| R6 | 基本数量（数量）・単位・単価・残数量は必須（0不可） | `在庫マスタ登録/変更画面` 各チェック |
| R7 | 出庫数量は必須・0超 | `出庫登録/変更画面` 各チェック |
| R8 | 手配分割は **手配数量 = 分割数量1+2+3** の整合必須 | `手配データ分割画面` 分割画面チェック |

| R10 | 当月残数量 = 前月残 + 当月入庫 − 当月出庫（金額も同式） | `⑧入出庫状況確認` 入出庫確認データ取り込み |
| R11 | 当月残=0 → 警告「在庫が0です」／0<当月残<安全在庫 → 「安全在庫以下です。発注して下さい。」／未入庫の発注あり → 「発注予定又は発注済みです。」 | 同左（Q列に文字列、条件付き書式で塗り） |
| R12 | 入庫取消は入庫済み行のみ、入庫は未入庫行のみ有効 | `⑤入庫マクロ` 入庫者及び入庫日セット |
| R13 | 削除前に確認メッセージ（はい/いいえ） | 受付/入庫/在庫マスタ/出庫/分割各画面 |
| R14 | 採番は T_採番テーブル の Read→+1→Write（排他なし） | 手配管理NO採番 / 出庫管理NO採番 |
| R15 | 一覧は行頭に連番（NO）を表示、A列はヘッダー2行目 | 各データ取り込み |
| R16 | 発注依頼下書きは「内容」欄="削除"で除外し、依頼ボタンでDBへ一括INSERT | `②発注依頼マクロ` |

## 3. Excel特有の制約の読み解き

### 3.1 制約の一覧（現状の作り → 本質要件 → 新システムでの扱い）

| ID | 現状の作り（Excel的実装） | 本質的な業務要件 | 新システムでの扱い |
|---|---|---|---|
| C1 | 一覧＝フラット行＋オートフィルタ。DBに一意/NotNull制約なし | 一覧検索・絞り込み・並べ替え。マスタは一意 | テーブル定義＋一意制約/NotNull。グリッドUIで検索・ソート標準化 |
| C2 | 状態を **受付日/入庫日のNULL** で表現（未受付/未入庫） | 伝票に「状態」と確定者・確定日時の記録が必要 | 明示的なステータス列＋状態遷移管理＋確定者/確定日時の保持 |
| C3 | 削除は「内容」欄選択→**物理DELETE**（`delete * from ...`） | 「削除」は業務操作だが取り消し不能・履歴なし | 論理削除（削除フラグ）＋削除前確認＋操作ログ。物理削除禁止 |
| C4 | 入力はUserForm、一覧行はプルダウン選択で操作 | 入力フォームと一覧操作の両方が必要 | フォーム（入力）とグリッド（一覧）の分離。直接編集は権限/項目単位で制御 |
| C5 | 画面遷移を **T1セルフラグ/グローバル変数（wコード等）** で保持 | 前画面・操作者・選択データの保持が必要 | セッション/画面状態（戻る履歴・ログインユーザー・選択コンテキスト） |
| C6 | 処理中に `ScreenUpdating=False`/`DisplayAlerts=False` | 誤操作防止と画面安定 | モーダル確認・処理中表示・ロール別画面制御を標準化 |
| C7 | 一覧クリアは `Range("A3:AZ500000").Delete`、最終行判定は `Cells(500000,...).End(xlUp)`（50万行級一括操作） | 表示領域の管理 | DB問合せベースのページング表示。全件一括は不要 |
| C8 | 帳票はExcelレイアウト＋PrintPreview。発注依頼表はA4横・タイトル行$4:$4・フッター頁/総頁 | 固定帳票が必要 | 帳票定義（項目・レイアウト・印刷条件）として要件化。PDF/印刷出力へ |
| C9 | DBはDAOで都度OPEN/CLOSE、SQLは**文字列連結**（`"delete * from " & テーブル名 & ...`） | データアクセス層の分離と安全なクエリ | リポジトリ層・パラメータ化クエリ・接続プール |
| C10 | 二次元配列→Range一括代入（`Range("A3:R"&n)=配列`） | 一覧データの高速描画 | グリッドのデータソース化（サーバーサイド成形） |
| C11 | **入庫/出庫を登録しても残数量は自動更新されない**。月次で「一括変更」により残数量を補正 | 在庫残高の管理はあるが**手動・月次締め補正** | 登録時のリアルタイム在庫更新（トランザクション）。月次締めは「期首残」の別概念へ |
| C12 | 警告（在庫0/安全在庫以下）を **Q列の文字列** で表示 | 補充判断のための警告表示 | アラート一覧/ダッシュボード化。マスタ属性から自動発注提案まで拡張可能 |
| C13 | 採番は採番テーブルを Read→+1→Write（**排他なし**、欠番・競合の恐れ） | 連番による一意な識別子 | DB自動採番（シーケンス/AUTO_INCREMENT） |
| C14 | 一部シートで Protect/Unprotect（パスワードなし、しかも受付/入庫は保護コメントアウト） | 入力可能列の制限 | ロール/権限による入力制御 |
| C15 | **実在しないシート「発注状況詳細確認」** を参照（入出庫状況確認のダブルクリック） | コード別発注履歴の詳細表示（設計意図） | 詳細画面を新規に実装するか、機能要否を確認 |
| C16 | **デッドコード**: 手配分割画面（起動がコメントアウト）、受付変更データ保存（未呼び出し）、全シート一括クリア（未割当ボタン） | 過去にあった/計画された機能の名残 | 機能要否をヒアリング。必要なら再実装 |
| C17 | 発注登録画面のコード候補を **在庫マスタシートの表示範囲（RowSource）** に依存 | 選択肢データがマスタと同期している必要 | DB/マスタから直接選択 |
| C18 | 出庫登録で **残数量・安全在庫との整合チェックなし**（在庫超過・負在庫が可能） | 出庫時の残数確認が必要 | 登録時に在庫残数チェック（不足は警告/ブロック） |
| C19 | **T_在庫使用量データ** と使用量系クエリがVBA未参照 | 製造計画連動の使用量管理（休眠中） | 用途をヒアリング。不要なら新DBへ移行しない |
| C20 | `注番` カラムが T_在庫発注データ に実在しない（分割機能で書き込み） | 分割手配の注番管理（未完成） | 分割機能の要否と合わせて要件を確定 |
| C21 | **審査承認欄**シートが誰からも参照されず残存 | 発注依頼表の承認フロー（作成/審査/承認）の設計意図 | 承認フロー要件として要否を確認 |
| C22 | 帳票（発注依頼表）に記名・承認欄が無い（別シートにのみ存在） | 承認ワークフローの要否 | ワークフロー要件（承認ステップ）の要否を確認 |
| C23 | 集計はAccessクエリで実施（Q_入庫/出庫データ集計→Q_入出庫状況確認）。当月締め | 期間集計・月次締めの要件 | 集計ロジックをDBビュー/サービス化。集計期間（当月）定義を確定 |
| C24 | 状態を**条件付き書式の色**で表現（発注状況確認: 入庫日あり=灰色。入出庫状況確認: 警告文字=灰色） | 一覧の行状態を視覚区別 | 行状態表示（バッジ/色分け）はDBステータス値から導出 |
| C25 | **On Error 処理が皆無**（`On Error` 不使用） | 失敗時はVBAのエラー停止→開発者へ連絡の運用（マニュアル） | 例外ハンドリング＋エラーログ＋ユーザー向けメッセージ標準化 |

### 3.2 現行ツールのリスク・課題（デッドコード・不整合含む）

1. **発注状況詳細確認シート不存在**（C15）: 入出庫状況確認のコード列ダブルクリックで `Sheets("発注状況詳細確認")` を参照するため**実行時エラーになる**。実運用では使えない未完成機能
2. **手配分割機能が無効化**（C16/C20）: 起動ハンドラ（`⑦入庫` のダブルクリック）が完全にコメントアウトされ、画面を開く手段がない。さらに `注番` カラムがDBに無く、`データセット` プロシージャも未定義（コメントアウト）。分割実行時にエラーとなるため、現行では実質的に利用不可
3. **在庫残高の自動更新なし**（C11）: 入庫・出庫を登録しても在庫マスタの残数量は変わらない。月初に「入出庫状況確認→一括変更」を実行しない限り残数量が古いままで、**出庫時も残数不足の警告がない**（C18）。負在庫・過剰出庫が可能
4. **物理削除**（C3）: 受付/入庫/在庫マスタ/出庫の削除はDELETE文。誤操作の取り消し不可・監査ログなし
5. **SQL文字列連結**（C9）: `delete * from T_... where 管理NO='...'`。値にシングルクォートが入るとSQL破壊。注入リスク
6. **排他なし採番**（C13）: 複数PC同時利用で管理NO重複の可能性。ただし現行は単独運用前提
7. **担当者・権限概念の欠如**（C14）: 担当者は「名前を選ぶ」だけで認証なし。シート保護もパスワードなし、しかも受付/入庫では保護自体がコメントアウトされ**全セル編集可能**
8. **On Error無し**（C25）: 例外は未処理でVBA標準のエラー停止。途中までDB更新して異常終了するリスク（トランザクションなし）
9. **デモデータの残存**（`在庫マスタ登録画面`）: フォーム起動時に「A0001/鉛筆/茨城文具」等のサンプル値が自動入力される（テスト残骸）。実データ登録と誤認する恐れ
10. **金額計算のゼロ除算**（R9）: `基本数量=0` のとき `数量/基本数量*単価` がエラーになる。DBには0やNULLが混在可能
11. **採番・状態の欠番問題**: 受付取消・入庫取消・削除で管理NOに欠番が生じる。`H0000000001` など10桁固定文字列のため、1億件超で形式崩壊
12. **発注依頼画面のNO振り直し**（`発注登録データセット`）: `A列 = 最終行-1` 方式のため、行削除後にNOが重複/不整合になり得る

### 4.2 非機能要件

- **同時利用者**: 現行は単独運用（Excel/Windows1台）。マルチPC運用にする場合はWeb/クライアント/サーバー化と接続排他が必要（要確認）
- **レスポンス**: 一覧表示はページング/絞り込み前提。件数規模（要確認）
- **権限**: 少なくとも「担当者」ごとの操作記録。承認フロー（作成/審査/承認）導入可否は要確認（C22）
- **監査**: 全操作（登録/変更/削除/受付/入庫/出庫/締め）の操作者・日時・内容のログ保持。現行の登録者/登録日/受付者/入庫者等は踏襲
- **バックアップ**: DBの定期バックアップ、削除前の退避（論理削除）
- **データ保持期間**: 現行は削除のみで保持期間の概念なし（要確認）
- **移行要件**: 既存 data.accdb の実データ移行、採番値（手配/出庫管理NO）の引き継ぎ、NULL状態（未受付/未入庫）の復元

- 削除は論理削除＋操作ログ（C3）
- 承認フロー（作成/審査/承認）導入時は、状態遷移を発注データに付与

### 4.7 移行要件

- data.accdb の実データを移行（実運用DBでの確認が必要。テンプレートは0件）

- 状態復元: 受付日/入庫日のNULL有無からステータス列へ変換
- 分割手配（注番）・使用量データは要否確認後に移行判断
- 実在しないシート（発注状況詳細確認）分のデータは発注データから復元可

## 5. 要確認事項（運用・ヒアリングで確定すべきこと）

1. 実運用DB（data.accdb）のデータ規模・件数・コード体系

9. 物理削除→論理削除への変更可否・保持期間（C3）
10. 発注依頼表の承認欄（作成/審査/承認）を帳票に含めるか

12. 現行のバックアップ運用
